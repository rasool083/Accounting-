# سامانه حسابداری کارگاه — Design Specification

## هدف
تبدیل نمونه فعلی `Accounting-` به یک سامانه حسابداری/فروش و تسویه قابل استفاده برای کارگاه، با تاریخ جلالی، موتور دقیق تسویه و بهره روزشمار، ثبت چک، موجودی و گزارش‌گیری؛ با معماری‌ای که بعداً بتواند به Supabase و Android متصل شود بدون بازنویسی منطق مالی.

## وضعیت فعلی
کد فعلی یک UI تک‌صفحه‌ای RTL با localStorage دارد. `data.js` شامل Store، تبدیل تاریخ جلالی/میلادی، موجودیت‌های people/products/prices/sales/receipts/audit و موتور اولیه FIFO است. `ui.js` صفحات dashboard، people، products، prices، sales، receipts، statement، month، audit، backup و settings را رندر می‌کند. `index.html` هنوز نسخه قدیمی و عمدتاً monolithic را نیز در خود دارد؛ بنابراین اولین کار فنی حذف دوگانگی و تبدیل آن به entry point ماژولار است.

## معماری
```text
UI
 ↓
Application services
 ↓
Domain / financial engine
 ↓
Repository interface
 ↓
LocalStorage adapter  →  Supabase adapter (مرحله بعد)
```

اصل مهم: UI نباید مستقیماً فرمول‌های مالی را اجرا کند. تمام محاسبات مهم باید در توابع مستقل و قابل تست قرار گیرند. Repository نیز باید قابل تعویض باشد تا localStorage فعلی بعداً با Supabase جایگزین شود.

## مدل داده پیشنهادی
هر رکورد دارای `id`، تاریخ ثبت، و در صورت نیاز `createdAt/updatedAt` است. تاریخ‌های مالی ورودی به صورت رشته جلالی `YYYY/MM/DD` نگهداری می‌شوند و تاریخ میلادی برای محاسبات فقط در لایه date utility تولید می‌شود.

موجودیت‌های پایه:
- `people`
- `products`
- `prices`
- `sales`
- `saleReturns`
- `purchases`
- `purchaseReturns`
- `receipts`
- `payments`
- `checks`
- `accounts`
- `transfers`
- `expenses`
- `incomes`
- `adjustments`
- `audit`
- `settings`

برای سازگاری با داده فعلی، مهاجرت باید فیلدهای فعلی را حفظ کند و فقط فیلدهای جدید را با مقدار پیش‌فرض اضافه کند.

## سیاست تسویه
1. فروش‌ها بر اساس تاریخ جلالی و سپس `id` مرتب می‌شوند.
2. دریافت‌های مؤثر فقط رکوردهای غیر «باطل» و غیر «برگشتی» هستند.
3. دریافت‌ها FIFO به فروش‌های واجد شرایط تخصیص می‌یابند.
4. مانده هر فروش جداگانه نگهداری می‌شود تا سود فقط روی اصلِ تسویه‌نشده محاسبه شود.
5. ضریب سود از tierهای تنظیمات و مبنای روزشمار (`dayBasis`) محاسبه می‌شود.
6. محاسبه historical balance باید به تاریخ محاسبه صریح وابسته باشد و از `today` پنهان استفاده نکند.
7. چک آینده و چک وصول‌شده باید وضعیت‌های مستقل داشته باشند؛ اثر مالی هر وضعیت در domain engine تعریف می‌شود، نه در UI.
8. سیاست تأخیر چک برگشتی باید قابل تنظیم باشد تا بتوان سناریوی «عدم مطالبه سود تأخیر» را دقیقاً اعمال کرد.

## امنیت و دسترسی
نسخه فعلی local-only است و PIN صرفاً قفل رابط است؛ این به‌عنوان احراز هویت واقعی تلقی نمی‌شود. در فاز Supabase، احراز هویت باید با Supabase Auth و Row Level Security انجام شود. کاربر اصلی حق ورود/ویرایش داده‌های عملیاتی دارد؛ شریک/کاربر مشاهده‌ای فقط داده‌های مجاز را می‌بیند؛ مشتری در فاز پرتال فقط رکوردهای خودش را مشاهده می‌کند.

## تست
قبل از هر منطق تولیدی جدید، تست واحد باید رفتار مورد نظر را ثابت کند. حداقل مجموعه تست:
- تبدیل تاریخ‌های شناخته‌شده و مرزهای سال
- leap-year جلالی
- diff روزها
- FIFO یک فروش/یک دریافت
- چند فروش/یک دریافت
- یک فروش/چند دریافت
- دریافت قبل از فروش و credit
- دریافت برگشتی/باطل
- سود صفر، tier اول و tierهای بعدی
- historical calculation
- چک آینده، وصول‌شده، برگشتی
- backup/restore
- مهاجرت داده قدیمی

## معیار پذیرش
- نسخه جدید بدون از دست رفتن داده فعلی load شود.
- عملیات اصلی فروش و دریافت قابل ثبت و برگشت باشد.
- مانده و سود با موتور مستقل محاسبه شوند و UI فقط نتیجه را نمایش دهد.
- تاریخ جلالی در تمام فرم‌های مالی قابل ورود و در محاسبات دقیق باشد.
- پشتیبان JSON کامل قابل ایجاد و بازیابی باشد.
- تست‌های واحد مالی سبز باشند.
- کد از `index.html` monolithic جدا شده و entry point فقط ساختار صفحه و importها را نگه دارد.
- هیچ ادعای اتصال زنده به Supabase/Android/WebMCP تا زمانی که واقعاً پیاده‌سازی و تست نشده، در UI یا README درج نشود.
