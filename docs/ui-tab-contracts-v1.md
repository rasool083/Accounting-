# قرارداد رابط کاربری سربرگ‌به‌سربرگ — v1

## هدف
این سند قرارداد اجرایی UI پروژه است. بعد از قفل‌شدن هر سربرگ، اصلاح سربرگ بعدی حق تغییر رفتار، چیدمان یا قرارداد داده سربرگ قبلی را ندارد مگر با یک تغییر نسخه‌دار و تست بازگشتی.

## اصل ضد برهم‌ریختگی
- یک سیستم Modal مشترک: همه فرم‌های ورود/ویرایش در پنجره مرکزی، جمع‌وجور، RTL و واکنش‌گرا.
- یک مالک برای هر رفتار UI؛ از زنجیره patchهای متوالی که همان تابع را دوباره تعریف می‌کنند استفاده نشود.
- هر سربرگ فقط فایل/ماژول‌های محدوده خودش را تغییر می‌دهد.
- قبل از هر تغییر: تست رفتاری همان سربرگ Red/Green.
- بعد از Green: تست بازگشتی کل سربرگ‌های قفل‌شده.
- سربرگ قفل‌شده فقط با تغییر نسخه قرارداد باز می‌شود.
- منطق مالی و داده از UI جدا می‌ماند.

## پیش‌نیاز صفر — پوسته مشترک UI
- [ ] Modal مرکزی و mobile-safe
- [ ] فرم‌های ایجاد و ویرایش یک الگوی واحد
- [ ] لیست رکوردها زیر/کنار صفحه اصلی بدون فرم باز ثابت
- [ ] فاصله، دکمه، جدول، وضعیت و رنگ‌ها دارای owner واحد
- [ ] حذف/ویرایش با تأیید و بدون پاک‌کردن خاموش
- [ ] هیچ CSS/JS override زنجیره‌ای که owner قبلی را بی‌اثر کند
- [ ] 360/390/430px و desktop بررسی شوند

## 1. داشبورد
- [ ] فقط نمایش؛ فرم ایجاد ندارد.
- [ ] KPIها از منبع محاسباتی واحد.
- [ ] کلیک روی KPI فقط ناوبری/فیلتر است و داده را تغییر نمی‌دهد.
- [ ] اصلاحات سربرگ‌های دیگر ظاهر داشبورد را نشکند.

## 2. اشخاص
- [ ] دکمه «افزودن» فقط Modal مرکزی را باز کند.
- [ ] فرم ایجاد و ویرایش دقیقاً یک ساختار داشته باشد.
- [ ] لیست اشخاص همیشه زیر عنوان و خارج از فرم ثابت دیده شود.
- [ ] نقش‌ها قابل توسعه باشند؛ مشتری/تأمین‌کننده/شریک/کارگر/سایر مطابق قرارداد.
- [ ] وضعیت فعال/غیرفعال قابل ویرایش.
- [ ] بسته شرایط پرداخت قابل انتخاب باشد؛ تغییر بسته آینده سوابق قبلی را بازنویسی نکند.
- [ ] سناریو: ایجاد، ویرایش، غیرفعال‌سازی، حذف فقط در صورت مجازبودن.

## 3. کالا و موجودی
### کالا
- [ ] ایجاد/ویرایش کالا در Modal مرکزی.
- [ ] واحد پایه، واحد بسته، ضریب بسته، واحد قیمت‌گذاری.
- [ ] فعال/غیرفعال.
### انبار
- [ ] انبارها موجودیت مستقل و قابل ایجاد/ویرایش/غیرفعال‌سازی.
- [ ] کد، نام، نوع، فعال، توضیحات.
- [ ] انواع مصوب: مواد اولیه، محصول تولیدی، بازرگانی، سایر.
- [ ] حذف فیزیکی فقط اگر هیچ اثر/حرکت وابسته وجود ندارد؛ در غیر این صورت غیرفعال.
- [ ] انتقال/حرکت موجودی هیچ‌گاه با ویرایش مستقیم موجودی خام جایگزین نشود.
### موجودی
- [ ] هر حرکت به کالا + انبار + تاریخ + نوع حرکت + مقدار + واحد + مرجع سند متصل باشد.
- [ ] انبار انتخابی در لیست قابل مشاهده باشد.
- [ ] سناریوهای خرید، فروش، برگشت، انتقال، اصلاح و تولید پوشش داده شوند.

## 4. قیمت‌ها
- [ ] ایجاد و ویرایش قیمت در Modal مرکزی.
- [ ] قیمت عمومی و در صورت فعال‌شدن قرارداد، قیمت اختصاصی مشتری.
- [ ] تاریخ اعتبار و تاریخچه حفظ شود.
- [ ] قیمت قبلی overwrite نشود.
- [ ] واحد قیمت‌گذاری از قرارداد کالا پیروی کند.

## 5. فروش
- [ ] فرم فاکتور در Modal مرکزی و صفحه اصلی فقط لیست را نشان دهد.
- [ ] واحد پایه و واحد بسته هر دو قابل انتخاب.
- [ ] مقدار فروش بر اساس واحد انتخابی به مقدار پایه تبدیل شود.
- [ ] مثال قراردادی: 1 کارتن با ضریب 36 = 36 واحد پایه.
- [ ] قیمت واحد متناظر با واحد انتخابی/قرارداد کالا محاسبه شود؛ محاسبه نباید «1» را با «36» اشتباه بگیرد.
- [ ] مبلغ ناخالص، تخفیف و مبلغ نهایی تفکیک شوند.
- [ ] تخفیف خط فاکتور ممکن باشد.
- [ ] تخفیف مستقل بدون کالا نیز مجاز باشد؛ به‌صورت سند مالی مشخص با ارجاع به مشتری/حساب، نه «فاکتور جعلی» در منطق اصلی.
- [ ] سناریوهای فروش با واحد پایه، بسته، تخفیف، چند ردیف و ویرایش پوشش داده شوند.
- [ ] اثر فروش بر مانده و موجودی دوباره‌شماری نشود.

## 6. خرید
- [ ] فرم در Modal مرکزی.
- [ ] مشتری/تأمین‌کننده، کالا، واحد، مقدار، قیمت، تاریخ.
- [ ] خرید و برگشت خرید دو عملیات مستقل و قابل ردگیری.
- [ ] اثر خرید روی موجودی و بدهی با OperationID مشترک.

## 7. دریافت / پرداخت / خزانه
- [ ] یک سطح UI مشترک برای دریافت و پرداخت.
- [ ] نوع تراکنش به‌صورت واضح: دریافت یا پرداخت.
- [ ] نقد/کارت/حواله در دسته نقدی قابل مدیریت؛ چک چرخه جدا دارد.
- [ ] رنگ ردیف‌ها فقط نشانه کمکی باشد، نه منطق اصلی.
- [ ] برای وصول چک/دریافت انتخاب حساب خزانه از فهرست حساب‌های موجود.
- [ ] حساب‌های مالی مستقل از اشخاص.
- [ ] انتقال داخلی بین حساب‌ها Operation واحد با دو اثر.

## 8. چک‌ها
- [ ] ثبت و ویرایش در Modal مرکزی.
- [ ] وضعیت‌ها مطابق قرارداد: نزد ما، تودیع‌شده، وصول‌شده/پاس‌شده، برگشتی، خرج‌شده، باطل.
- [ ] انتخاب «در چه حسابی وصول شد» از حساب‌های خزانه.
- [ ] انتخاب «به چه شخصی/حسابی تودیع شد» مطابق قرارداد پرداخت/خزانه.
- [ ] وضعیت در خود جدول با کشوی سریع قابل تغییر باشد.
- [ ] رنگ سبز برای وصول‌شده، قرمز برای برگشتی؛ رنگ صرفاً راهنمای بصری.
- [ ] برگشتی به‌صورت یک Event/Operation ثبت شود؛ وضعیت قبلی حذف نشود.
- [ ] یک چک برگشتی بتواند یک یا چند جایگزین داشته باشد.
- [ ] UI جایگزینی در Modal ثانویه کوچک باز شود تا جدول اصلی شلوغ نشود.
- [ ] جایگزین می‌تواند چک جدید یا نقد/تراکنش جدید باشد.
- [ ] هیچ جایگزینی اصل بدهی را دوباره به‌عنوان بدهی مستقل ایجاد نکند.
- [ ] سناریو هدف: چک دریافتی → تودیع → وصول؛ و نیز وصول → برگشت → چند جایگزین.

## شرایط پرداخت و پله‌ها — زیرماژول مستقل
- [ ] بسته شرایط: PackageID, PackageCode, Name, Active, Notes.
- [ ] پله: TierID, PackageID, TierNo, MaxDays, MonthlyRate, Active, Notes.
- [ ] ایجاد/ویرایش پله در Modal جدا.
- [ ] فعال/غیرفعال‌سازی هر پله مستقل.
- [ ] حذف فیزیکی پله فقط در صورت نداشتن وابستگی تاریخی؛ در غیر این صورت غیرفعال.
- [ ] حداکثر 5 پله فقط برای UI اولیه است؛ منطق موتور نباید به 5 hard-code شود.
- [ ] پله منتخب: کوچک‌ترین MaxDays فعال که >= روز واقعی باشد.
- [ ] نرخ منتخب روی کل روز واقعی اعمال شود.
- [ ] مثال‌های اجباری: 30، 31، 45، 60، 61 روز؛ پله غیرفعال؛ پله ناقص؛ Override؛ تغییر بسته از تاریخ جدید.
